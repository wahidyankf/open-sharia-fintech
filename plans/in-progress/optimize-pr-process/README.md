## Outcome

Make planning, pull-request authoring, review, fixing, quality gates, and closure easy for humans to
read and audit. “Junior engineer” means someone just out of a coding bootcamp, with no university
computer-science background. A merged PR remains an educational team record, not an agent-only log.

## Hard Boundaries

- Prefer prose, existing GitHub features, and existing workflows. Add mechanical enforcement only
  when evidence shows it is necessary; every line of tooling becomes maintenance burden.
- [Judgment call] Keep each PR cohesive and readable: at most 400 changed hand-authored lines and 20
  hand-authored files. Split larger work into sequential, independently stable PRs.
- Use one reusable worktree per repository for this entire plan. Never use stacked dependent PRs;
  merge, verify, and resync before opening the next dependency.
- A PR description explains outcome, reason, scope/non-goals, reading order, verification, risk,
  integration safety, and rollback in plain language. Mermaid is optional and needs prose fallback.
- Reviews use native GitHub findings and same-thread replies. Every AI-authored body, review, and
  reply ends with `Generated by AI`; the PR artifact holds the auditable history.
- A fixer critically chooses `fix`, `reject-with-reason`, `defer-with-reason`, or `clarify`. It does
  not blindly agree, widen scope, or hide unresolved work.
- [Judgment call] Aim to converge in cycles 1–3. Cycles 4–5 are autonomous recovery; stop before
  cycle 6 and ask a human only when the bounded process cannot safely finish. Humans may read every
  PR after merge.
- Preserve trunk stability with the lightest suitable “feature flag”: dormant documentation,
  ordered activation, compatibility bridge, runtime flag, or atomic slice.
- Keep public/private rules semantically aligned through exact merged pins and explicit deviations.
  Byte identity applies only where an existing surface contract requires it.

## Scope and Delivery Shape

In scope: PR descriptions and size, educational review comments, reply/resolve behavior, scope and
cycle gates, planning lifecycle, repo-rule propagation, necessary binding updates, dogfood evidence,
idea retirement, knowledge capture, and plan closure. Out of scope: a new review bot, database,
parser, merge queue, universal runtime flag, or unrelated CI cleanup.

Plan assembly must finish before idea or implementation delivery. The exact unstacked order begins
`FOUNDATION → REQUIREMENTS → DESIGN → EXECUTION → ACTIVATE → PUB-IDEAS → PRIV-IDEAS`; see
[delivery.md](./delivery.md#sequential-plan-assembly). Later public/private waves consume exact
merged-green pins and record discharge or deliberate deviation.
