# Multi-Harness Binding: Mechanical Generation and the Parity Guard (Rules 4-5)

Standards 4 and 5 of the [Multi-Harness Binding Convention](../multi-harness-binding.md): generation
must be mechanical, and a deterministic guard enforces it stays that way.

## Rule 4 — Mechanical Generation (AD4)

Any binding file that must exist (Tier-2 bridge or an approved Tier-1 thin pointer) is **generated
by the repo's CLI tooling** from `AGENTS.md`. The generator follows the same model as the existing
agent-sync generator. Hand-maintaining a binding file is not permitted; it guarantees eventual drift.

The generator is invoked via an npm script (mirroring the pattern of the existing agent-sync script)
and is re-run whenever `AGENTS.md` changes.

## Rule 5 — Deterministic Parity Guard (AD7)

A deterministic, agent-free CLI check runs in the pre-push hook (alongside the existing vendor-audit
and cross-vendor-parity checks). It performs two assertions:

1. **Byte-equality**: for each generated binding file, re-derive it from `AGENTS.md` in memory and
   assert it matches the committed file exactly (a sync no-op, analogous to the existing agent-sync
   validator).
2. **Catalog completeness**: assert every binding directory present on disk has a row in
   `docs/reference/platform-bindings.md`.

The check exits non-zero on any mismatch, blocking the push until the generator is re-run or the
stale directory is removed.

**Important distinction**: this guard catches _internal_ drift (a committed binding falling out of
sync with `AGENTS.md`). It is deterministic and runs in milliseconds. It is distinct from the
periodic compatibility-audit workflow (see
[repo-harness-compatibility-quality-gate.md](../../../workflows/repo/repo-harness-compatibility-quality-gate.md)),
which catches _external_ drift — an upstream harness changing its conventions — and requires
web-research-backed agent work.
