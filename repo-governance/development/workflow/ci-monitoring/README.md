# CI Monitoring Convention

- [Overview and Absolute Floor](./01-overview-and-absolute-floor.md) — Why CI monitoring must be rate-limit-safe, the required default poll interval, and the hard 2-minute minimum spacing. Use when starting CI monitoring, to confirm the default poll interval and the absolute floor on polling frequency.
- [Runner Contention Across the OSE Repos (Read First)](./02-runner-contention-across-the-ose-repos.md) — Runner capacity is shared and finite across the OSE repos; contention is expected, and the correct response is to wait and check, not assume a defect. Use when a CI run is queued or stalled with no progress, before assuming the pushed code is broken.
- [Principles and Conventions Implemented](./03-principles-and-conventions-implemented.md) — The principles and companion conventions that safe CI monitoring respects. Use when tracing why this convention's monitoring rules exist back to the principles and conventions they respect.
- [Purpose and Scope](./04-purpose-and-scope.md) — Why this convention exists, its target audience, and exactly what it covers versus what it defers to companion conventions. Use when checking whether a CI-monitoring question is in scope for this convention or belongs to a companion convention instead.
- [Rate Limit Budget Facts](./05-rate-limit-budget-facts.md) — The GitHub API rate-limit quota, reset window, and why a tight poll loop or gh run watch exhausts it. Use when estimating whether a polling approach will exhaust the GitHub API rate limit.
- [ScheduleWakeup Every 2 Minutes (Required Default)](./06-schedulewakeup-every-2-minutes.md) — The required default monitoring pattern — schedule a wakeup, then issue one status check per wakeup until the run completes. Use as the default way to poll any CI run to completion.
- [Manual Poll Loop With 2-Minute Sleep (Unavoidable Loop Cases)](./07-manual-poll-loop-with-2-minute-sleep.md) — The fallback poll pattern when ScheduleWakeup is unavailable, and why gh run watch is prohibited. Use only when ScheduleWakeup is unavailable and a manual poll loop is unavoidable.
- [Trigger Discipline](./08-trigger-discipline.md) — Rules preventing redundant concurrent CI runs — never trigger the same workflow more than once every 10 minutes. Use before triggering a CI workflow, to confirm no run for it is already active.
- [Diagnosing a Stuck Self-Hosted Runner Job](./09-diagnosing-a-stuck-self-hosted-runner-job.md) — How to tell a genuinely hung job step from a merely slow one, and remediate by cancelling and rerunning only the affected jobs. Use when a self-hosted-runner job step shows zero progress for an extended period and contention has already been ruled out.
- [Retriggering a Stuck Run With No Contention (PR Branches)](./10-retriggering-a-stuck-run-with-no-contention.md) — Rebase-and-push as the last resort for a genuinely wedged worktree-to-pr run once contention has been ruled out. Use when a worktree-to-pr run is stuck with contention already ruled out and cancel/rerun does not clear it.
- [Recovery When Rate-Limited](./11-recovery-when-rate-limited.md) — The scheduled-wait recovery procedure for an HTTP 403 from gh, and why a retry loop is forbidden. Use when a gh command returns HTTP 403 during CI monitoring.
- [Locating the Failing Task in a Parallel Runner's Log](./12-locating-the-failing-task-in-a-parallel-runners-log.md) — Why the tail of a parallel Nx runner's log belongs to whichever task finished last, not the one that failed, and how to find the real failure. Use when diagnosing a failed CI job whose log is produced by a parallel task runner like Nx.
- [Application in Plan Execution (Step 2c)](./13-application-in-plan-execution-step-2c.md) — How the plan-execution workflow's Step 2c post-push CI verification applies this convention's monitoring rules. Use when executing Step 2c of the plan-execution workflow, for the exact required monitoring pattern and forbidden shortcuts.
- [Examples](./14-examples.md) — Worked pass/fail examples covering correct polling, trigger checks, and rate-limit recovery versus forbidden stream-watching and tight loops. Use when you need a concrete example of correct or incorrect CI monitoring behavior.
