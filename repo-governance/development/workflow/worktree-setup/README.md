# Worktree Toolchain Initialization

- [Principles and Conventions Implemented](./01-principles-and-conventions-implemented.md) — The principles the worktree toolchain initialization practice respects, and its lack of a direct Layer 2 convention. Use when tracing why the two-step worktree init exists back to the principles it respects.
- [The Rule](./02-the-rule.md) — The mandatory two-step npm install / doctor --fix sequence, run order, the --fix flag, and the shared cargo target-directory symlink it provisions. Use as the exact commands to run, in order, right after creating or entering a worktree.
- [Independent Drift Layers and the `postinstall` Hook](./03-independent-drift-layers-and-the-postinstall-hook.md) — The two independent kinds of toolchain drift a worktree session can hit, and why the postinstall hook's error-swallowing means only the explicit doctor --fix call forces convergence. Use when explaining why both npm install and npm run doctor -- --fix are independently required, not either alone.
- [Dependency Isolation, Language Breadth, and Idempotency](./04-dependency-isolation-language-breadth-and-idempotency.md) — Why node_modules is not shared across worktrees, why worktrees routinely need many language toolchains, and why doctor --fix is cheap to run unconditionally. Use when explaining why every worktree entry needs the two-step init regardless of stated task scope.
- [What Goes Wrong Without Both Steps, and Nx's `node_modules` Dependency](./05-what-goes-wrong-and-nx-node-modules-dependency.md) — The concrete failure modes (build, test, lint, cache, cryptic errors) from skipping the two-step init, and why Nx's caching depends on consistent node_modules state. Use when diagnosing a build, test, lint, or Nx-cache failure that may trace back to a skipped worktree init step.
- [Per-Project Dependency Restoration for Some Language Ecosystems](./06-per-project-dependency-restoration.md) — The doctor --fix gap for F#/.NET projects, which need an explicit dotnet restore step the toolchain-level fix does not cover. Use when `nx affected -t test:quick` fails on an F# project with a missing-dependency error right after provisioning a worktree.
- [Sibling-Repo Relative Paths From Inside a Worktree (Multi-Repo Plans)](./07-sibling-repo-relative-paths.md) — Why a naive ../sibling-repo path breaks from inside a worktree, and the correct nesting-adjusted relative path for a multi-repo worktree-to-pr plan. Use when authoring or reviewing a multi-repo delivery-checklist command that references a sibling repo with a relative path.
- [Absolute Source Paths in Delivery-Checklist Commands (Same-Repo Worktree vs. Primary Checkout)](./08-absolute-source-paths-in-delivery-checklist-commands.md) — Why a hardcoded absolute path to a repo's primary checkout silently resolves to stale content instead of the worktree's in-progress copy, and how to verify it before running. Use before running any delivery-checklist command that reads from an absolute path into a repo the same plan is also modifying.
- [When This Applies](./09-when-this-applies.md) — The five triggering conditions for the two-step worktree init, and that it applies regardless of stated task scope. Use when deciding whether a given worktree entry needs the two-step init.
- [Step-by-Step Procedure](./10-step-by-step-procedure.md) — The five numbered steps from creating a worktree through confirming both init commands completed. Use as a walkthrough when creating a worktree and running its toolchain init for the first time.
- [Notes for AI Agents](./11-notes-for-ai-agents.md) — The MUST-run-both-steps rule for agents, and why re-running the init (not re-provisioning) is the correct response to missing worktree dependencies mid-session. Use when an agent creates or enters a worktree, or discovers missing dependencies/build output mid-session.
